1. DIMENSION LOAD LOGIC
=======================================================================

Q1. HOW DO YOU POPULATE dim_patient FROM THE patients TABLE?
------------------------------------------------------------
A dimension load reads the source table, cleans the
attributes, stamps validity, and inserts. Four steps, in that order.

      -- once, before any data
      INSERT INTO dim_patient (patient_key, ...)
      VALUES (-1, 'UNKNOWN', ...);            -- the unknown member

      -- then the real rows
      INSERT INTO dim_patient (
          patient_id, mrn, first_name, last_name, date_of_birth, gender,
          effective_from, effective_to, is_current)
      SELECT
          patient_id,                          -- natural key, kept for lookup
          mrn, first_name, last_name,
          <cleaned date_of_birth>,
          <cleaned gender>,
          '1900-01-01',                        -- valid from
          '9999-12-31',                        -- valid to
          1                                    -- this is the current version
      FROM source.patients;

  1. SURROGATE KEY. patient_key is generated by the warehouse.

  2. NATURAL KEY RETAINED. patient_id stays as a column so the next load can
     find "the current row for this source patient" without guessing.

  3. CLEAN THE ATTRIBUTES ON THE WAY IN.  

  4. STAMP SCD2 VALIDITY even on a first load, so the incremental path in Q3
     has something to compare against.



Q2. HOW DO YOU POPULATE dim_date (ONE-TIME LOAD)?
--------------------------------------------------
Calendars are GENERATED,  every attribute is derivable from the date itself.

      FOR each day d in [start .. end]:
          date_key       := YYYYMMDD as an integer
          full_date      := d
          calendar_month := format(d, 'YYYY-MM')
          year, quarter, month, day_of_month, day_of_week,
          day_of_year, week_of_year
          is_weekend     := day_of_week IN (6,7)



Q3. HOW DO YOU HANDLE UPDATES TO DIMENSIONS?
---------------------------------------------
The decision is per dimension, and it is made before writing any code: does
history matter for this attribute?

      Type 1 -- overwrite       history does not matter
      Type 2 -- new version     history matters

  TYPE 1 IS THE DEFAULT, and most dimensions qualify. A department's floor
  number changing is a correction to a current fact, not an event worth
  preserving. Small dimensions are simply rebuilt each load: no comparison,
  no versioning, write whatever the source says now.

  TYPE 2 IS FOR ATTRIBUTES WHERE OVERWRITING WOULD REWRITE HISTORY. Correct
  a patient's recorded gender in 2026 and a Type 1 overwrite makes every
  2023 encounter report the new value -- last year's published figures stop
  reconciling. Type 2 keeps each fact pointing at the row as it was recorded
  at the time.

  Here that means dim_patient and dim_provider are Type 2; the other six
  dimensions are Type 1 or static.

  THE TYPE 2 ALGORITHM:

      FOR each source row:
          find the current dimension row for this natural key
              (WHERE natural_key = source.key AND is_current = 1)

          IF none exists:
              INSERT as a new row, is_current = 1

          ELIF its attributes differ from the source:
              close the old row:  effective_to = TODAY - 1, is_current = 0
              insert a new row:   effective_from = TODAY,   is_current = 1

          ELSE:
              do nothing

  DETECTING "differ" IS THE HARD PART, and it depends on what the source
  gives you:

      if the source has updated_at    compare timestamps -- exact, cheap
      if it does not                  compare CONTENT, by hashing the
                                      attributes and comparing hashes

  This source has no change-tracking column of any kind (finding B9), so
  content hashing is the only option available:

      incoming := MD5(attr1 | attr2 | ... )
      current  := MD5(the same attributes from the stored row)

2. FACT TABLE LOAD LOGIC
=======================================================================

Q4. FOR EACH ENCOUNTER, HOW DO YOU LOOK UP DIMENSION KEYS?
-----------------------------------------------------------
Every dimension is joined once, on its NATURAL key, and the surrogate key
that comes back is what lands on the fact row.


  DATE KEYS NEED NO JOIN AT ALL. date_key is YYYYMMDD, so it is computed
  directly from the source datetime:

          date_key           := CAST(FORMAT(encounter_date,'YYYYMMDD') AS INT)
          discharge_date_key := same, or NULL if not discharged


Q5. HOW DO YOU CALCULATE PRE-AGGREGATED METRICS?
-------------------------------------------------
Anything that needs aggregating is computed in its OWN pass, into a staging
table keyed on encounter_id, then joined in. Four passes here.

      A. BILLING -> encounter grain
         SELECT encounter_id,
                SUM(claim_amount),
                SUM(allowed WHERE status <> 'Denied'),
                SUM(allowed WHERE status =  'Denied'),
                worst status wins (Denied > Pending > Paid)
         FROM source.billing GROUP BY encounter_id

      B. COUNTS
         SELECT encounter_id, COUNT(DISTINCT diagnosis_id)
         FROM source.encounter_diagnoses GROUP BY encounter_id
         -- same shape for procedures

      C. THE READMISSION FLAG -- the expensive one
         SELECT DISTINCT index.encounter_id
         FROM source.encounters index
         JOIN source.encounters ret
           ON  ret.patient_id     =  index.patient_id
           AND ret.encounter_id  <>  index.encounter_id
           AND ret.encounter_date >  index.discharge_date
           AND ret.encounter_date <= index.discharge_date + 30 DAYS
         WHERE index.encounter_type = 'Inpatient'

      D. DERIVED INLINE, no staging needed
         length_of_stay_minutes := TIMESTAMPDIFF(MINUTE, admit, discharge),
                                   or NULL if discharge < admit
         patient_age_years      := TIMESTAMPDIFF(YEAR, dob, encounter_date)



Q6. HOW DO YOU HANDLE MISSING DATA?
------------------------------------
One policy, applied everywhere:

      missing dimension reference   -> unknown member (-1), ROW IS KEPT
      missing measure               -> COALESCE to 0
      missing date                  -> NULL key where nullable
      no encounter_date             -> REJECT the row; a fact with no date
                                       cannot sit on any timeline
      impossible value              -> NULL the derived measure, keep the row
      value outside a known domain  -> map to 'Unknown', keep the row
      duplicate junction row        -> collapsed by the bridge primary key

  THE GOVERNING RULE: NEVER DROP A FACT TO PRESERVE TIDINESS. An encounter
  that happened belongs in the warehouse even if its provider reference is
  broken. The row loads, the gap is visible, and someone can investigate.


=======================================================================
3. BRIDGE TABLE LOAD LOGIC
=======================================================================

Both bridges load AFTER the fact, because they need encounter_key -- which
the fact insert assigns.


Q7. HOW DO YOU POPULATE bridge_encounter_diagnoses?
----------------------------------------------------

      INSERT IGNORE INTO bridge_encounter_diagnoses
          (encounter_key, diagnosis_key, diagnosis_sequence)
      SELECT f.encounter_key,          -- from the fact, by encounter_id
             ddx.diagnosis_key,        -- from the dimension, by CODE
             ed.diagnosis_sequence     -- carried through; 1 = principal
      FROM source.encounter_diagnoses ed
      JOIN fact_encounters f    ON f.encounter_id  = ed.encounter_id
      JOIN source.diagnoses  sd ON sd.diagnosis_id = ed.diagnosis_id
      JOIN dim_diagnosis    ddx ON ddx.icd10_code  = sd.icd10_code;


  JOIN ON CODE, NOT ID. The hop through source.diagnoses turns the source's
  diagnosis_id into its ICD-10 code, because dim_diagnosis was conformed on
  code. If the source ever holds two ids for I10, both rows resolve to one
  dimension row and the counts stay whole.

  INSERT IGNORE against PRIMARY KEY (encounter_key, diagnosis_key). The key
  already prevents duplicates; IGNORE states the intent rather than relying
  on a constraint violation. The same diagnosis coded twice on one visit is a
  data-entry artifact, not two diagnoses.



Q8. HOW DO YOU POPULATE bridge_encounter_procedures?
-----------------------------------------------------

      INSERT IGNORE INTO bridge_encounter_procedures
          (encounter_key, procedure_key, procedure_date_key)
      SELECT f.encounter_key,
             dpx.procedure_key,        -- from the dimension, by CPT CODE
             CAST(FORMAT(ep.procedure_date,'YYYYMMDD') AS INT)
      FROM source.encounter_procedures ep
      JOIN fact_encounters f    ON f.encounter_id  = ep.encounter_id
      JOIN source.procedures sp ON sp.procedure_id = ep.procedure_id
      JOIN dim_procedure    dpx ON dpx.cpt_code    = sp.cpt_code;


  A procedure has its own date, distinct from
  the encounter's: during a five-day stay, procedures happen on different
  days. That makes it a property of the encounter-procedure PAIR, so it
  cannot live on the fact. It is also what makes this a bridge rather than a
  bare link table, the same role diagnosis_sequence plays next door.


=======================================================================
4. REFRESH STRATEGY
=======================================================================

Q9. HOW OFTEN WOULD YOU LOAD? (daily / incremental / full refresh)
------------------------------------------------------------------
NIGHTLY, off-peak. Clinical analytics answers questions about yesterday and
last quarter.

Full vs incremental is decided per table, by size:

      dim_date                       never refreshed
      the five small dimensions      FULL reload -- all under 50 rows
      dim_provider                   FULL compare, SCD2
      dim_patient                    FULL compare, SCD2
      fact_encounters                INCREMENTAL
      bridges                        incremental, following the fact
      agg table                      FULL rebuild



Q10. HOW WOULD YOU HANDLE LATE-ARRIVING FACTS?
-----------------------------------------------

      within 30 days                  automatic -- the restatement window
      NEW, older than 30 days         caught by the watermark; a backdated
                                      record still gets a new encounter_id
   

   Mitigation is a weekly reconciliation: compare COUNT(*) and SUM(allowed_amount) per month, source
  vs warehouse, and queue any diverging month for full restatement. That
  converts undetectable drift into a detected discrepancy with a defined
  repair path.




WHAT etl_load_log DOES, AND WHAT IT DOES NOT
---------------------------------------------
The only state that survives between runs. Three jobs.

  1. HOLDS THE HIGH-WATER MARK

  2. MAKES FAILURE SAFE.

  3. COUNTS WHAT WAS CORRECTED.
