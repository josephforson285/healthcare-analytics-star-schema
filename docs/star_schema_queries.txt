METHOD
------
MEASUREMENT VARIANCE -- READ BEFORE THE NUMBERS BELOW
------------------------------------------------------
Every timing here was re-measured in a second session on the same machine.
All figures moved by almost exactly 2x -- uniformly, in both the OLTP and
star columns -- while the query plans and intermediate row counts stayed
IDENTICAL to the row. That is machine speed varying, not query behaviour.

Treat absolute seconds as +/-25% at best. The RATIOS held across both
sessions (Q1 slower both times; Q3 ~4x faster both times; Q4 ~1.5x both
times) and the conclusions rest on those, not on any single wall-clock
figure. Full comparison and the ruled-out hypotheses:
results/measurement_sessions.txt


Identical to Part 2: MySQL 8.4.10, same machine, same 300,000-encounter
dataset, median of 3 warm runs after a discarded warm-up.

EQUIVALENCE IS VERIFIED, NOT ASSUMED
Every star query's full output was diffed row-by-row against its OLTP
counterpart. All four are byte-identical: Q1 864 rows, Q2 top-20, Q3 12
rows, Q4 288 rows. A faster query that returns different numbers is not
an optimisation, so this check came before any timing was recorded.

Two real defects were caught by that diff and fixed:
  * Q3 -- Cardiology and Psychiatry both score 21.84%, and with no
    secondary sort key the two engines ordered the tie differently.
    Values were always identical; a tie-break was added to both queries.
  * Q4 -- the star version under-reported by $84,420,895. The ETL splits
    the source's single allowed_amount into allowed vs denied, so the
    equivalent figure is SUM(allowed_amount + denied_amount). Not a bug
    in the warehouse; a genuine semantic difference that had to be made
    explicit. See the Q4 note below.

=======================================================================
Q1: Monthly Encounters by Specialty  --  0.606s -> 0.308s  (1.97x faster)
=======================================================================

    SELECT
        CONCAT(FLOOR(a.ym / 100), '-', LPAD(a.ym % 100, 2, '0'))  AS month,
        sp.specialty_name,
        a.encounter_type,
        a.encounters,
        a.unique_patients
    FROM (
        SELECT
            FLOOR(f.date_key / 100)         AS ym,   -- YYYYMMDD -> YYYYMM
            f.specialty_key,
            f.encounter_type,
            SUM(f.encounter_count)          AS encounters,
            COUNT(DISTINCT f.patient_key)   AS unique_patients
        FROM fact_encounters f
        GROUP BY ym, f.specialty_key, f.encounter_type
    ) a
    JOIN dim_specialty sp ON sp.specialty_key = a.specialty_key
    ORDER BY month, sp.specialty_name, a.encounter_type;

THE FIRST VERSION OF THIS QUERY WAS SLOWER THAN THE OLTP ORIGINAL, AND
THAT IS THE MOST USEFUL THING IN THIS DOCUMENT.

Written the obvious way -- join dim_date and dim_specialty, then
GROUP BY d.calendar_month, sp.specialty_name -- it measured 0.746s against
the OLTP query's 0.581s. A 1.3x REGRESSION, on the query the star schema
was supposed to help.

The diagnosis was initially wrong. It was attributed to
COUNT(DISTINCT patient_key) being immune to dimensional modelling, and to
fact_encounters being twice the size of encounters on disk. Both are true
and neither was the cause.

The actual cause: GROUPING ON TWO VARCHARs PULLED IN FROM JOINED
DIMENSIONS. That cost more than the joins saved. The same effect had
already been measured on dim_encounter_type (see Q5) -- grouping on a
joined string ran 2.5x slower than grouping on one already present in the
fact row -- and the lesson simply was not applied here.

THE FIX, and it needed no schema change at all:

  * FLOOR(date_key / 100) turns YYYYMMDD into YYYYMM. The month falls out
    of the surrogate key arithmetically, so dim_date is not joined AT ALL.
    This is a side benefit of choosing YYYYMMDD for date_key rather than a
    meaningless sequence.
  * Group by specialty_KEY, an integer on the fact, not specialty_NAME.
    dim_specialty is then joined to the 864 OUTPUT rows instead of to
    300,000 input rows.

    naive star (join then group on names)   0.746 s
    integer-first (group then join names)   0.287 s
    OLTP original                          0.581 s

0.746s -> 0.287s, turning a 1.3x regression into a 2.0x improvement.
Output verified byte-identical to both the naive star version and the OLTP
original, all 864 rows.

WHAT THIS ACTUALLY DEMONSTRATES

A star schema does not make a badly written query fast. It removes joins
from the critical path, and then it is still possible to put the cost back
by grouping and sorting wide text instead of narrow keys.

It is the same principle that makes Q2b beat OLTP Q2: aggregate on integer
keys, attach the descriptive text to the surviving rows afterwards. Q4
gained 3.3x from exactly the same rewrite.

An aggregate table at month/specialty/type grain would make this a
sub-millisecond lookup, and is deliberately NOT built -- at 0.3s the query
does not need one, and adding a summary table for every query that could
be faster is how a warehouse becomes an unmaintainable pile of them.

Q2: Top Diagnosis-Procedure Pairs  --  10.188s -> 0.026s  (392x faster)
=======================================================================

    SELECT dd.icd10_code, dd.icd10_description,
           dp.cpt_code,  dp.cpt_description,
           a.encounter_count
    FROM agg_diagnosis_procedure_pair a
    JOIN dim_diagnosis dd ON dd.diagnosis_key = a.diagnosis_key
    JOIN dim_procedure dp ON dp.procedure_key = a.procedure_key
    ORDER BY a.encounter_count DESC
    LIMIT 20;

Measured: 0.026s vs 10.188s -- 392x faster.

WHY IT IS FASTER

The OLTP version built 2,060,000 intermediate rows and sorted them to
return 20. This reads 1,200 rows that were computed once, at load time,
and never rebuilt.

That is the entire mechanism, and it must be attributed correctly:
THIS SPEEDUP IS PRECOMPUTATION, NOT DIMENSIONAL MODELLING. An equivalent
aggregate table could have been built directly off the OLTP schema and
would have performed the same. Claiming 392x as evidence that "star
schemas are faster" would be false.

What the star schema actually contributes is a stable grain to aggregate
FROM. The ETL builds this table from the bridges, whose grain is declared
and enforced by a primary key. Built off the OLTP junction tables, the
same aggregate would have to defend against duplicate rows, split ICD-10
codes under two ids, and NULL foreign keys on every run -- see the eight
guards in sql/05_etl.sql.

Q2b: The same question WITHOUT the aggregate table  --  10.188s -> 2.072s
=======================================================================

    SELECT dd.icd10_code, dd.icd10_description,
           dp.cpt_code,  dp.cpt_description, x.encounter_count
    FROM (
        SELECT bd.diagnosis_key, bp.procedure_key,
               COUNT(DISTINCT bd.encounter_key) AS encounter_count
        FROM bridge_encounter_diagnoses  bd
        JOIN bridge_encounter_procedures bp ON bp.encounter_key = bd.encounter_key
        GROUP BY bd.diagnosis_key, bp.procedure_key
        ORDER BY encounter_count DESC
        LIMIT 20
    ) x
    JOIN dim_diagnosis dd ON dd.diagnosis_key = x.diagnosis_key
    JOIN dim_procedure dp ON dp.procedure_key = x.procedure_key
    ORDER BY x.encounter_count DESC;

Measured: 2.072s vs 10.188s -- 4.9x faster.

THIS IS THE HONEST STAR-SCHEMA-ONLY NUMBER FOR Q2.

The fan is still there. This query still forms ~2.06 million pair rows,
because pairing diagnoses with procedures inherently produces pairs and no
schema can answer the question without forming them. Three things changed:

1. ROW WIDTH. The OLTP version dragged icd10_description VARCHAR(200) and
   cpt_description VARCHAR(200) through the sort, because they appear in
   the GROUP BY. Here the grouping happens on two integers and the text is
   joined on afterwards, against 20 surviving rows. Sorting 2M narrow rows
   instead of 2M wide ones is most of the 4.9x.

2. FEWER TABLES IN THE HOT PATH. The OLTP query joins four tables to form
   the pairs; this joins two.

3. NO MEASURE IS REACHABLE. Neither bridge contains money. The 6.9x
   revenue inflation demonstrated in README.md cannot be written from this
   shape, because there is nothing to sum. The wrong answer went from
   "discouraged by documentation" to "structurally impossible" -- which is
   worth more than the 4.9x.

Q3: 30-Day Readmission Rate  --  0.429s -> 0.349s  (1.23x faster)
=======================================================================

    SELECT
        sp.specialty_name,
        SUM(f.is_index_admission)                            AS inpatient_discharges,
        SUM(f.is_readmission_30d)                            AS readmissions_30d,
        ROUND(100 * SUM(f.is_readmission_30d)
                  / NULLIF(SUM(f.is_index_admission), 0), 2) AS readmission_rate_pct
    FROM fact_encounters f
    JOIN dim_specialty   sp ON sp.specialty_key = f.specialty_key
    WHERE f.is_index_admission = 1
    GROUP BY sp.specialty_name
    ORDER BY readmission_rate_pct DESC, sp.specialty_name;

Measured: 0.349s vs 0.429s -- 1.23x faster.

WHY IT IS FASTER

The self-join is gone. Not optimised -- gone. It was executed ONCE, by the
ETL, and its answer stored in a single TINYINT column:

    INSERT INTO _readmit
    SELECT DISTINCT i.encounter_id
    FROM healthcare_oltp.encounters i
    JOIN healthcare_oltp.encounters r
      ON  r.patient_id     =  i.patient_id
      AND r.encounter_id  <>  i.encounter_id
      AND r.encounter_date >  i.discharge_date
      AND r.encounter_date <= i.discharge_date + INTERVAL 30 DAY
    WHERE i.encounter_type = 'Inpatient' AND i.discharge_date IS NOT NULL;

What remains at query time is a filtered scan and a GROUP BY over 12
specialties, supported by idx_type_readmit.

This is the mechanism the whole exercise is about, and it is worth stating
plainly: THE WORK DID NOT GET CHEAPER. IT MOVED. The same self-join runs
once per load instead of once per analyst per question. If nobody asks the
readmission question, the star schema is strictly slower overall, because
the ETL did work nobody needed.

A note on modesty: 1.23x is the smallest speedup of the four,
because the OLTP version was already fast. The brief's hint predicted a
self-join disaster; the automatic FK index on patient_id meant it never
happened. The gain is real but it is 0.6 seconds, not a rescue.

Also worth noting: the readmission DEFINITION now lives in the ETL, in one
place, instead of being re-implemented in every analyst's query. Ten
analysts writing that self-join by hand would produce several subtly
different definitions -- some restricting the return to inpatient, some
using >= instead of >, some forgetting to exclude the index encounter
itself. Consistency is arguably worth more here than the 0.6 seconds.

Q4: Revenue by Specialty & Month  --  1.081s -> 0.189s  (5.72x faster)
=======================================================================

    SELECT
        d.calendar_month            AS month,
        sp.specialty_name,
        SUM(f.encounter_count)      AS claims,
        ROUND(SUM(f.allowed_amount + f.denied_amount), 2) AS total_allowed
    FROM fact_encounters f
    JOIN dim_date        d  ON d.date_key      = f.date_key
    JOIN dim_specialty   sp ON sp.specialty_key = f.specialty_key
    GROUP BY d.calendar_month, sp.specialty_name
    ORDER BY d.calendar_month, sp.specialty_name;

Measured: 0.189s vs 1.081s -- 5.72x faster.

WHY IT IS FASTER

The billing table is gone from the query. In the OLTP schema the money
lives in billing and the date lives in encounters, so 300,000 rows must be
joined before anything can be summed. Here the money is already ON the
encounter row, put there once by the ETL.

The join chain went from 4 tables to 3, and the two remaining joins are
against a 1,096-row and a 61-row dimension rather than a 300,000-row
transaction table.

The month is also no longer derived by DATE_FORMAT on every row, which is
the same saving Q1 got -- and, as Q1 shows, that saving alone is not large.
The billing join accounts for part of it; the integer-first rewrite (grouping
on FLOOR(date_key/100) and specialty_key rather than on the joined VARCHARs)
accounts for 3.3x of it on its own.

ON (allowed_amount + denied_amount)

The ETL splits the source's single allowed_amount column into two measures
by claim status. Reproducing the OLTP figure exactly therefore requires
adding them back: 754,318,058 + 84,420,895 = 838,738,953, matching to the
cent.

The split is kept deliberately. This schema can now report realisable
revenue, denied revenue and denial rate by specialty with no reference to
claim_status at all. The OLTP query cannot separate them without an extra
predicate -- and, more importantly, most analysts writing that query would
never notice they had counted $84.4M of rejected claims as revenue.

That is a correctness improvement, not a performance one, and it is
arguably the more valuable of the two.

Q5 (supplementary): what dim_encounter_type is for
=======================================================================

    SELECT
        et.type_name, et.is_emergency, et.is_overnight,
        SUM(f.encounter_count)                        AS encounters,
        ROUND(AVG(f.length_of_stay_minutes) / 60, 1)  AS avg_stay_hours,
        ROUND(SUM(f.allowed_amount + f.denied_amount)
              / SUM(f.encounter_count), 2)            AS avg_revenue_per_encounter
    FROM fact_encounters     f
    JOIN dim_encounter_type  et ON et.encounter_type_key = f.encounter_type_key
    GROUP BY et.type_name, et.is_emergency, et.is_overnight
    ORDER BY encounters DESC;

Not one of the four business questions. It is here because the four
questions never join dim_encounter_type, and that needs explaining rather
than leaving as an apparent oversight.

They read encounter_type straight off the fact row instead, where it also
lives as a degenerate attribute. That choice is measured, not assumed:

    GROUP BY f.encounter_type   (string already on the fact)   1.49 s
    GROUP BY et.type_name       (joined from the dimension)    3.68 s

2.5x slower. Grouping on a joined VARCHAR costs more than grouping on one
already present in the row. For a query that only needs the type's NAME,
the fact column is strictly the better choice, and the dimension would be
pure overhead.

So the dimension earns its place a different way. It closes an attribute
domain the source leaves open -- encounter_type is a free-text VARCHAR(50)
with no CHECK constraint (finding B4), so 'ER', 'er' and 'Emergency' are
all storable, and a foreign key to a three-row table makes a fourth value
impossible rather than merely unlikely. And it gives is_emergency and
is_overnight somewhere to live; those have no home on the fact row, and
the query above cannot be written without them.

Result:

    type_name    is_emergency  is_overnight  encounters  avg_stay_hours
    Outpatient        0             0          210,359        1.4
    ER                1             0           59,702        6.5
    Inpatient         0             1           29,939      131.5

A three-row dimension is not automatically over-modelling. It is
over-modelling when it carries nothing the fact row could not, which is
the case this one had to answer.


=======================================================================
WHAT THE NUMBERS ACTUALLY SHOW
=======================================================================

Aggregate result: 12.30 seconds of OLTP query time became 0.87 seconds
(Q1 + Q2 + Q3 + Q4), a 14.1x overall improvement. But the aggregate hides
the shape of the result, which is the interesting part:

  ONE query got dramatically faster       Q2, and mostly by precomputation
  TWO got substantially faster            Q4 5.72x, Q1 1.97x
  ONE got moderately faster               Q3 1.23x

  Q1 and Q4 only reached those figures after being rewritten. As first
  written -- joining dimensions then grouping on their VARCHAR columns --
  Q1 was 1.3x SLOWER than OLTP and Q4 only 1.8x faster. Grouping on integer
  keys already present on the fact, and joining the text to the output rows
  instead, moved them to 1.97x and 5.72x. No schema change was involved.

The mechanisms, ranked by how much they actually delivered:

  1. PRECOMPUTATION (Q2 392x, Q3 1.23x). Doing expensive work once at load
     time instead of once per query. By far the largest effect, and not
     specific to star schemas.

  2. COLLAPSING JOINS BY DENORMALISING (part of Q4's 5.72x). Putting the measure on
     the fact row and the attribute on the dimension row. This is the
     dimensional modelling contribution proper. Real, and moderate.

  3. NARROWER INTERMEDIATE ROWS (Q2b 4.9x). Grouping on integer keys and
     joining wide text on afterwards.

  4. NOT DERIVING GROUPING KEYS (part of Q1 and Q4). Storing '2024-06'
     once per day rather than computing it 300,000 times per query.
     Measurable, small.

And the cost side, which a before/after table tends to hide:

  * fact_encounters is 2.2x the size of encounters on disk (105 MB vs
    47.6 MB). Every query pays that scan cost, including the ones that
    read none of the precomputed columns.
  * The ETL takes 68 seconds. That is 68 seconds of work performed
    whether or not anyone asks a question.
  * The warehouse is a second copy of the data and is stale between loads.

Q1 is the single most useful result in this table, because it is the one
that failed. A star schema is not uniformly faster. It is faster for the
queries you designed it for, and slower for the ones you did not.
