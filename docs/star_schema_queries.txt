The four queries rewritten for the star schema
=======================================================================

For each query, as the brief asks:
    1. the SQL, optimized for the star schema
    2. execution time vs the original
    3. improvement factor
    4. why it is faster


METHOD
------
Same machine, same 300,000-encounter dataset, median of 9 warm runs after
two discarded warm-up passes. The brief asks for an estimate; these are
MEASURED, which is strictly better.

SUMMARY
=======================================================================

  Query  OLTP       Star       Improvement   Main mechanism
  -----  ---------  ---------  ------------  -------------------------
  Q1     0.566 s    0.294 s    1.92x faster  integer-first aggregation
  Q2     9.874 s    0.024 s     411x faster  pre-aggregated table

=======================================================================
Q1: MONTHLY ENCOUNTERS BY SPECIALTY
=======================================================================

1. THE SQL

    SELECT
        CONCAT(FLOOR(a.ym / 100), '-', LPAD(a.ym % 100, 2, '0'))  AS month,
        sp.specialty_name,
        a.encounter_type,
        a.encounters,
        a.unique_patients
    FROM (
        SELECT
            FLOOR(f.date_key / 100)         AS ym,   -- YYYYMMDD -> YYYYMM
            f.specialty_key,
            f.encounter_type,
            COUNT(*)                        AS encounters,
            COUNT(DISTINCT f.patient_key)   AS unique_patients
        FROM fact_encounters f
        GROUP BY ym, f.specialty_key, f.encounter_type
    ) a
    JOIN dim_specialty sp ON sp.specialty_key = a.specialty_key
    ORDER BY month, sp.specialty_name, a.encounter_type;

2. EXECUTION TIME

    0.294 s  vs  0.566 s original

3. IMPROVEMENT FACTOR

    1.92x faster

4. WHY IT IS FASTER

  DENORMALIZATION -- specialty_name is one hop from the fact on a 12-row
  dim_specialty, instead of two hops through providers.

  NO DATE JOIN AT ALL -- date_key is YYYYMMDD, so FLOOR(date_key/100)
  yields the month arithmetically. The OLTP query recomputes DATE_FORMAT
  for 300,000 rows on every execution, and that derived value cannot use
  idx_encounter_date for grouping. A key format chosen for readability
  turned out to remove a join.

  SORTING INTEGERS, NOT STRINGS -- the largest single factor, and worth
  stating plainly because the FIRST version of this query was SLOWER than
  the OLTP original.

  NOT faster because of better indexes, and NOT because of
  COUNT(DISTINCT patient_key) -- that cost is identical in both schemas.
  Dimensional modelling reduces join depth; it has no effect on a
  distinct-count, which remains the largest component of the 0.294 s.

Q2: TOP DIAGNOSIS-PROCEDURE PAIRS
=======================================================================

1. THE SQL

    SELECT
        dd.icd10_code,
        dd.icd10_description,
        dp.cpt_code,
        dp.cpt_description,
        a.encounter_count
    FROM agg_diagnosis_procedure_pair a
    JOIN dim_diagnosis dd ON dd.diagnosis_key = a.diagnosis_key
    JOIN dim_procedure dp ON dp.procedure_key = a.procedure_key
    ORDER BY a.encounter_count DESC
    LIMIT 20;

2. EXECUTION TIME

    0.024 s  vs  9.874 s original

3. IMPROVEMENT FACTOR

    411x faster

4. WHY IT IS FASTER

  PRE-AGGREGATION, and it must be attributed correctly.


  THIS SPEEDUP IS PRECOMPUTATION. An equivalent
  aggregate table could have been built directly off the OLTP schema and
  would have performed the same.  


  For the star-schema-only figure, see Q2b.

Q2b: THE SAME QUESTION WITHOUT THE AGGREGATE TABLE
=======================================================================

1. THE SQL

    SELECT
        dd.icd10_code, dd.icd10_description,
        dp.cpt_code,  dp.cpt_description, x.encounter_count
    FROM (
        SELECT bd.diagnosis_key, bp.procedure_key,
               COUNT(DISTINCT bd.encounter_key) AS encounter_count
        FROM bridge_encounter_diagnoses  bd
        JOIN bridge_encounter_procedures bp ON bp.encounter_key = bd.encounter_key
        GROUP BY bd.diagnosis_key, bp.procedure_key
        ORDER BY encounter_count DESC
        LIMIT 20
    ) x
    JOIN dim_diagnosis dd ON dd.diagnosis_key = x.diagnosis_key
    JOIN dim_procedure dp ON dp.procedure_key = x.procedure_key
    ORDER BY x.encounter_count DESC;

2. EXECUTION TIME

    2.224 s  vs  9.874 s original

3. IMPROVEMENT FACTOR

    4.43x faster -- THE HONEST STAR-SCHEMA-ONLY FIGURE FOR Q2

4. WHY IT IS FASTER

  NARROWER INTERMEDIATE ROWS.  
 

  FEWER TABLES IN THE HOT PATH -- two bridges instead of four tables.

Q3: 30-DAY READMISSION RATE
=======================================================================

Definition assumed: the index event is an inpatient discharge; a
readmission is ANY subsequent encounter by the same patient within 30 days.
The brief says only "return within 30 days" and does not restrict the
return type. Full reasoning, both result sets, and the one-line change to
switch: etl-logic-walkthrough.md, "The one open question".

1. THE SQL

    SELECT
        sp.specialty_name,
        SUM(f.is_index_admission)                            AS inpatient_discharges,
        SUM(f.is_readmission_30d)                            AS readmissions_30d,
        ROUND(100 * SUM(f.is_readmission_30d)
                  / NULLIF(SUM(f.is_index_admission), 0), 2) AS readmission_rate_pct
    FROM fact_encounters f
    JOIN dim_specialty   sp ON sp.specialty_key = f.specialty_key
    WHERE f.is_index_admission = 1
    GROUP BY sp.specialty_name
    ORDER BY readmission_rate_pct DESC, sp.specialty_name;

2. EXECUTION TIME

    0.331 s  vs  0.421 s original

3. IMPROVEMENT FACTOR

    1.27x faster -- the smallest gain of the four, and the reason matters

4. WHY IT IS FASTER

  PRE-AGGREGATION. The self-join is not optimised, it is GONE. 

   The same self-join runs once per nightly load
  instead of once per analyst per question.

Q4: REVENUE BY SPECIALTY AND MONTH
=======================================================================

1. THE SQL

    SELECT
        CONCAT(FLOOR(a.ym / 100), '-', LPAD(a.ym % 100, 2, '0'))  AS month,
        sp.specialty_name,
        a.claims,
        a.total_allowed
    FROM (
        SELECT
            FLOOR(f.date_key / 100)     AS ym,
            f.specialty_key,
            COUNT(*)                    AS claims,
            ROUND(SUM(f.allowed_amount + f.denied_amount), 2) AS total_allowed
        FROM fact_encounters f
        GROUP BY ym, f.specialty_key
    ) a
    JOIN dim_specialty sp ON sp.specialty_key = a.specialty_key
    ORDER BY month, sp.specialty_name;

2. EXECUTION TIME

    0.162 s  vs  1.034 s original

3. IMPROVEMENT FACTOR

    6.38x faster -- the largest genuine gain, two mechanisms stacking

4. WHY IT IS FASTER

  FEWER JOINS -- a whole table leaves the query.  

  PRE-AGGREGATION.
