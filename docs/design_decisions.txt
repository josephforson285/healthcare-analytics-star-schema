PART 3.1 DELIVERABLE -- design_decisions.txt
Dimensional model design decisions, with the evidence behind each
=======================================================================

Every decision below is answered to later tackle Part 2 measurements in
docs/query_analysis.txt.

Kimball's four steps:
  1. Select the business process ..... clinical encounters and their billing
  2. Declare the grain ............... one row per encounter (Decision 1)
  3. Identify the dimensions ......... Decision 2
  4. Identify the facts .............. Decision 3


=======================================================================
DECISION 1: FACT TABLE GRAIN
=======================================================================

CHOICE: Option A -- one row per encounter. fact_encounters = 300,000 rows.

WHY

The evidence is Q2. Joining the two junction tables produced
intermediate rows from 300,000 encounters. When financial values are aggregated 
after this row multiplication, totals may be overstated substantially without the database raising an error.


Encounter grain is also the only grain at which all four business questions
can be answered:

  Q1 counts encounters and distinct patients ....... encounter grain
  Q3 counts inpatient discharges and readmissions .. encounter grain
  Q4 sums allowed_amount per claim ................. encounter grain (1:1)
  Q2 needs diagnosis x procedure pairs ............. bridge tables

Three of four questions want encounter grain. The fourth is served by
bridges without dragging the other three down with it.


=======================================================================
DECISION 2: DIMENSION TABLES
=======================================================================

Eight dimensions -- the six the brief lists, plus dim_diagnosis and
dim_procedure which the bridges require.

-----------------------------------------------------------------------
dim_date  
-----------------------------------------------------------------------
  date_key INT PK        -- YYYYMMDD, e.g. 20240612. Human-readable and
                            sorts correctly as an integer.
  full_date, year, quarter, month, calendar_month ('2024-06'),
  day_of_month, day_of_week, day_of_year, week_of_year, is_weekend

  WHY IT EXISTS AT ALL, when encounters already has a DATETIME:
  Q1 and Q4 both spend real time on DATE_FORMAT(encounter_date,'%Y-%m'),
  which recomputes a month string for 300,000 rows on every execution and
  makes idx_encounter_date unusable for grouping. A date dimension stores
  that string once per day instead of once per encounter. It also supplies calendar
  attributes SQL cannot derive  as the warehouse grows.


-----------------------------------------------------------------------
dim_patient  (SCD Type 2 structure)
-----------------------------------------------------------------------
  patient_key INT PK     -- surrogate
  patient_id INT         -- natural key from source
  mrn, first_name, last_name, date_of_birth, gender
  effective_from, effective_to, is_current   -- SCD2 

  NOTE ON AGE: age is deliberately NOT stored here.


-----------------------------------------------------------------------
dim_provider  (SCD Type 2 structure)
-----------------------------------------------------------------------
  provider_key INT PK, provider_id, first_name, last_name, credential,
  effective_from, effective_to, is_current


-----------------------------------------------------------------------
dim_department  (SCD Type 1)
-----------------------------------------------------------------------
  department_key INT PK, department_id, department_name, floor, capacity


-----------------------------------------------------------------------
dim_specialty  (SCD Type 1)
-----------------------------------------------------------------------
  specialty_key INT PK, specialty_id, specialty_name, specialty_code



-----------------------------------------------------------------------
dim_encounter_type  (SCD Type 1)
-----------------------------------------------------------------------
  encounter_type_key INT PK, type_name, is_emergency, is_overnight


-----------------------------------------------------------------------
dim_diagnosis
-----------------------------------------------------------------------
  diagnosis_key PK, diagnosis_id, icd10_code, icd10_description
  

  Required by the bridges (Decision 4).



=======================================================================
DECISION 3: PRE-AGGREGATED METRICS ON THE FACT TABLE
=======================================================================

FOREIGN KEYS
  date_key, discharge_date_key, patient_key, provider_key,
  department_key, specialty_key, encounter_type_key

DEGENERATE DIMENSION
  encounter_id 

  claim_status

MEASURES
  length_of_stay_minutes ... computed once at load from the two datetimes
  patient_age_years ........ age at the encounter date (see Decision 2)
  diagnosis_count .......... rows in the diagnosis bridge for this encounter
  procedure_count .......... rows in the procedure bridge
  claim_amount, allowed_amount, denied_amount
  is_readmission_30d ....... 0/1, precomputed
  is_index_admission ....... 0/1, inpatient with a discharge date

JUSTIFICATION, measure by measure

  diagnosis_count / procedure_count
  These are the counts that Q2's join was computing the expensive way. Any
  question of the form "how many diagnoses does an average ER visit carry"
  becomes AVG(diagnosis_count) against a single table -- no bridge, no
  join. The bridge is then needed only when the specific CODES
  matter, not merely how many there were.

  total allowed / claim / denied
  Collapses the billing join entirely. In the OLTP schema Q4 must join
  billing -> encounters before it can sum anything. Here the money is
  already on the encounter row.


  is_readmission_30d
  The single highest-value precomputation here. Q3's entire self-join. Q3 collapses to a GROUP BY
  over a stored column. It is faster because the expensive work
  was moved from query time to load time, where it happens once a day
  instead of once per analyst per question.

  length_of_stay_minutes
  TIMESTAMPDIFF on every row at query time, replaced by a stored integer.
 

  patient_age_years
  As above: time-variant, so it belongs to the event, not the person.


=======================================================================
SCHEMA ENFORCEMENT on Fact_table
=======================================================================

  fact_encounters    length_of_stay_minutes >= 0 (or NULL)
                     claim_amount / allowed_amount / denied_amount >= 0
                     allowed_amount + denied_amount <= claim_amount
                     diagnosis_count / procedure_count >= 0
                     is_index_admission, is_readmission_30d IN (0,1)
                     patient_age_years BETWEEN 0 AND 130 (or NULL)
                     encounter_type IN the three known values + 'Unknown'
                     claim_status  IN the four known values + 'Unknown'
  dim_date           month 1-12, quarter 1-4, day_of_week 1-7,
                     day_of_month 1-31, day_of_year 1-366, is_weekend 0/1
  dim_patient        effective_to >= effective_from, is_current IN (0,1)
  dim_provider       same
  dim_encounter_type is_emergency, is_overnight IN (0,1)
  bridge (diagnoses) diagnosis_sequence >= 1
  agg table          encounter_count > 0, total_allowed >= 0


=======================================================================
DECISION 4: BRIDGE TABLES
=======================================================================

DECISION: Yes. Two bridges, plus one aggregate table.

  bridge_encounter_diagnoses  (encounter_key, diagnosis_key,
                               diagnosis_sequence, is_principal)
  bridge_encounter_procedures (encounter_key, procedure_key,
                               procedure_date_key)

WHY BRIDGES ARE NECESSARY

A bridge keeps the many-to-many where it belongs. Outside the fact table,
at its own grain, joined only by queries that actually need codes.
