=======================================================================
PART 3.1 DELIVERABLE -- design_decisions.txt
Dimensional model design decisions, with the evidence behind each
=======================================================================

Every decision below is answered to later tackle Part 2 measurements in
docs/query_analysis.txt.

Kimball's four steps:
  1. Select the business process ..... clinical encounters and their billing
  2. Declare the grain ............... one row per encounter (Decision 1)
  3. Identify the dimensions ......... Decision 2
  4. Identify the facts .............. Decision 3


=======================================================================
DECISION 1: FACT TABLE GRAIN
=======================================================================

CHOICE: Option A -- one row per encounter. fact_encounters = 300,000 rows.

WHY

The evidence is Q2. Joining the two junction tables produced
intermediate rows from 300,000 encounters. When financial values are aggregated 
after this row multiplication, totals may be overstated substantially without the database raising an error.


Encounter grain is also the only grain at which all four business questions
can be answered:

  Q1 counts encounters and distinct patients ....... encounter grain
  Q3 counts inpatient discharges and readmissions .. encounter grain
  Q4 sums allowed_amount per claim ................. encounter grain (1:1)
  Q2 needs diagnosis x procedure pairs ............. bridge tables

Three of four questions want encounter grain. The fourth is served by
bridges without dragging the other three down with it.


=======================================================================
DECISION 2: DIMENSION TABLES
=======================================================================

Eight dimensions -- the six the brief lists, plus dim_diagnosis and
dim_procedure which the bridges require.

-----------------------------------------------------------------------
dim_date  
-----------------------------------------------------------------------
  date_key INT PK        -- YYYYMMDD, e.g. 20240612. Human-readable and
                            sorts correctly as an integer.
  full_date, year, quarter, month, calendar_month ('2024-06'),
  day_of_month, day_of_week, day_of_year, week_of_year, is_weekend

  WHY IT EXISTS AT ALL, when encounters already has a DATETIME:
  Q1 and Q4 both spend real time on DATE_FORMAT(encounter_date,'%Y-%m'),
  which recomputes a month string for 300,000 rows on every execution and
  makes idx_encounter_date unusable for grouping. A date dimension stores
  that string once per day instead of once per encounter. It also supplies calendar
  attributes SQL cannot derive  as the warehouse grows.


-----------------------------------------------------------------------
dim_patient  (SCD Type 2 structure)
-----------------------------------------------------------------------
  patient_key INT PK     -- surrogate
  patient_id INT         -- natural key from source
  mrn, first_name, last_name, date_of_birth, gender
  effective_from, effective_to, is_current   -- SCD2 machinery

  NOTE ON AGE: age is deliberately NOT stored here.

  NO row_hash here. Change detection still uses a
  content hash -- the source has no updated_at (B9) -- but every attribute
  it covers is already a column in this row, so the ETL recomputes it
  rather than storing a second copy. Measured before removal: the stored
  hash matched a recomputation on 50,000/50,000 rows. CHAR(32) x 50,001
  rows for a restatement of the row beside it.

  dim_provider carries no row_hash either. Its hash originally covered the
  source specialty_id and department_id -- left over from when this table
  still held those columns -- which made it look non-derivable and therefore
  necessary. It is not. A dimension should version on changes to attributes
  IT HOLDS, and dim_provider holds a name and a credential. Which specialty
  treated a patient is an attribute of the ENCOUNTER, and the fact already
  records specialty_key per row, so versioning a provider on a transfer
  would record in a second place what the fact already says.

  With the hash narrowed to name and credential, it is derivable from the
  row and no dimension in this warehouse persists one.

  WHAT THE SCD2 COLUMNS ARE FOR
  effective_from / effective_to  the window during which this version was
                                 true. A correction in 2026 closes the old
                                 row and opens a new one, so encounters
                                 from 2023 keep pointing at the old key and
                                 last year's reports still reconcile.
  is_current                     convenience flag. Derivable from
                                 (effective_to = '9999-12-31') and kept
                                 anyway: 1 byte, canonical Kimball, and it
                                 keeps every query readable.

  Stated plainly: all three are CONSTANT across all 50,001 rows today,
  because the ETL only performs a full load and never opens a second
  version. They are structure for the incremental path in etl_design.txt,
  which is what the brief's Part 3.4 asks about, and they were demonstrated
  working -- a source gender change produced two correctly dated versions.


-----------------------------------------------------------------------
dim_provider  (SCD Type 2 structure)
-----------------------------------------------------------------------
  provider_key INT PK, provider_id, first_name, last_name, credential,
  effective_from, effective_to, is_current

  Carries no specialty or department reference at all. The fact records
  provider_key AND specialty_key per encounter, so "which specialty was
  this provider in, and when" is answerable from the fact. Putting a
  reference here as well would add a dimension-to-dimension edge -- a
  snowflake -- for a column no query reads.

  Transfers still version correctly: the change-detection hash is computed
  from the source specialty_id and department_id at comparison time, even
  though neither is stored here.


-----------------------------------------------------------------------
dim_department  (SCD Type 1)
-----------------------------------------------------------------------
  department_key INT PK, department_id, department_name, floor, capacity


-----------------------------------------------------------------------
dim_specialty  (SCD Type 1)
-----------------------------------------------------------------------
  specialty_key INT PK, specialty_id, specialty_name, specialty_code



-----------------------------------------------------------------------
dim_encounter_type  (SCD Type 1)
-----------------------------------------------------------------------
  encounter_type_key INT PK, type_name, is_emergency, is_overnight


-----------------------------------------------------------------------
dim_diagnosis
-----------------------------------------------------------------------
  diagnosis_key PK, diagnosis_id, icd10_code, icd10_description
  procedure_key PK, procedure_id, cpt_code, cpt_description

  Required by the bridges (Decision 4).



=======================================================================
DECISION 3: PRE-AGGREGATED METRICS ON THE FACT TABLE
=======================================================================

FOREIGN KEYS
  date_key, discharge_date_key, patient_key, provider_key,
  department_key, specialty_key, encounter_type_key

DEGENERATE DIMENSION
  encounter_id -- no dimension table backs it; kept for drill-through
                   to the source only.

DENORMALISED COPY (not degenerate -- a real dimension exists)
  encounter_type -- also a column on dim_encounter_type, reached via
                   encounter_type_key above. Kept on the fact as well
                   because reading it here measured 2.5x faster than
                   joining the dimension for grouping (Q5).

STILL DEGENERATE
  claim_status -- 3 values, no dimension table, no attributes worth
                   modelling. Same reasoning that killed dim_specialty
                   as originally proposed, applied here and not reversed.

MEASURES
  length_of_stay_minutes ... computed once at load from the two datetimes
  patient_age_years ........ age at the encounter date (see Decision 2)
  diagnosis_count .......... rows in the diagnosis bridge for this encounter
  procedure_count .......... rows in the procedure bridge
  claim_amount, allowed_amount, denied_amount
  is_readmission_30d ....... 0/1, precomputed
  is_index_admission ....... 0/1, inpatient with a discharge date

JUSTIFICATION, measure by measure

  diagnosis_count / procedure_count
  These are the counts that Q2's join was computing the expensive way. Any
  question of the form "how many diagnoses does an average ER visit carry"
  becomes AVG(diagnosis_count) against a single table -- no bridge, no
  join, no fan. The bridge is then needed only when the specific CODES
  matter, not merely how many there were.

  total allowed / claim / denied
  Collapses the billing join entirely. In the OLTP schema Q4 must join
  billing -> encounters before it can sum anything. Here the money is
  already on the encounter row.


  is_readmission_30d
  The single highest-value precomputation here. Q3's entire self-join --
  30,000 index probes plus date-range evaluation -- is executed ONCE, by
  the ETL, and the answer is stored as a flag. Q3 collapses to a GROUP BY
  over a stored column.

  This is the real lesson of the whole. It is faster because the expensive work
  was moved from query time to load time, where it happens once a day
  instead of once per analyst per question.

  length_of_stay_minutes
  TIMESTAMPDIFF on every row at query time, replaced by a stored integer.
 

  patient_age_years
  As above: time-variant, so it belongs to the event, not the person.

  REMOVED: principal_diagnosis_key
  Was denormalised onto the fact from the diagnosis with sequence = 1. Most
  clinical reporting only wants the primary diagnosis, and this lets those
  queries avoid the bridge completely. Encounters with secondary diagnoses
  still have them in the bridge; this is a shortcut for the common case,
  not a replacement.


=======================================================================
SCHEMA ENFORCEMENT (not one of the brief's four decisions, but implied by
"all necessary foreign keys ... indexes")
=======================================================================

Section B of docs/00-findings-and-assumptions.md criticises the SOURCE
schema for being normalised but not well-constrained -- nine gaps, from
nullable-everywhere to free-text attribute domains. That criticism only
carries weight if this schema does better, and at first it did not: the
warehouse had zero CHECK constraints, and a plain UPDATE was able to write
a length of stay of -5000, revenue of -999, a 0/1 flag set to 7, and an
age of 500. All accepted without complaint.

The ETL guards (GUARD B1-B8) only protect the LOAD path. They say nothing
about anything that touches the table afterwards.

The source cannot be altered, so its gaps are documented. This schema is
ours, so its gaps are closed -- 27 CHECK constraints:

  fact_encounters    length_of_stay_minutes >= 0 (or NULL)
                     claim_amount / allowed_amount / denied_amount >= 0
                     allowed_amount + denied_amount <= claim_amount
                     diagnosis_count / procedure_count >= 0
                     is_index_admission, is_readmission_30d IN (0,1)
                     patient_age_years BETWEEN 0 AND 130 (or NULL)
                     encounter_type IN the three known values + 'Unknown'
                     claim_status  IN the four known values + 'Unknown'
  dim_date           month 1-12, quarter 1-4, day_of_week 1-7,
                     day_of_month 1-31, day_of_year 1-366, is_weekend 0/1
  dim_patient        effective_to >= effective_from, is_current IN (0,1)
  dim_provider       same
  dim_encounter_type is_emergency, is_overnight IN (0,1)
  bridge (diagnoses) diagnosis_sequence >= 1
  agg table          encounter_count > 0, total_allowed >= 0

Every one was verified against the loaded data before being added -- all 23
distinct rules returned zero violations -- so the constraints describe what
the ETL already produces rather than forcing a change to it.

Enforcement side by side:

                            FKs  UNIQUE  CHECK  columns NOT NULL
  healthcare_oltp (theirs)   10      1      0        22%
  healthcare_dw   (ours)     13      3     27        73%

Two notes on domain closure specifically. encounter_type and claim_status
are free-text VARCHAR(50) in the source with no CHECK -- findings B4 and B5
-- so 'ER', 'er' and 'Emergency' are all storable there. Here the domain is
finite and enforced, which is the second half of the guard: the ETL maps
unexpected values to 'Unknown' on the way in, and the constraint stops
anything else being written later.


=======================================================================
DECISION 4: BRIDGE TABLES
=======================================================================

DECISION: Yes. Two bridges, plus one aggregate table.

  bridge_encounter_diagnoses  (encounter_key, diagnosis_key,
                               diagnosis_sequence, is_principal)
  bridge_encounter_procedures (encounter_key, procedure_key,
                               procedure_date_key)

WHY BRIDGES ARE NECESSARY

A bridge keeps the many-to-many where it belongs. Outside the fact table,
at its own grain, joined only by queries that actually need codes.
